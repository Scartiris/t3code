# Localization

This fork ships **Simplified Chinese only**. There is no locale switcher and no
English fallback: `t()` reads one statically bundled catalog, so a missing entry
is a typecheck error rather than a silent fall back to English at runtime.

## Where it lives

`packages/i18n` is a **leaf package** holding the catalog (`src/zh-CN.ts`) and the
runtime (`src/index.ts`). It depends on nothing.

That placement is forced by the dependency graph, not by taste. `packages/contracts`
constructs user-facing error messages, and everything else depends on contracts —
so contracts cannot import from `@t3tools/shared` without a cycle. Putting the
catalog in its own leaf lets contracts, shared, client-runtime and the apps all
reach it.

`@t3tools/shared/i18n` re-exports the package and remains the public path for the
apps, so call sites did not have to churn.

```ts
import { t } from "@t3tools/shared/i18n";   // apps
import { t } from "@t3tools/i18n";          // packages/contracts and friends
```

## Keys

    <area>.<camelCaseFileName>.<name>

`settings.settingsPanels.appearanceHeading`, `chat.chatComposer.sendMessage`.
Keys are globally unique because file names are, which is what let ~120 agents
work in parallel without colliding: a full pass produced **zero key conflicts**.

Entries predating this rule (the original seed set, carried over from an earlier
localization attempt) keep their shorter names so their call sites do not churn.

## Placeholders

`{name}`, substituted verbatim by `t(key, { name })`. Chinese has no plural
forms, so there is no count-based branching to model — and the English
`count === 1 ? "file" : "files"` dance must be **deleted**, not translated, when
converting a call site.

Values may be `string | number | null | undefined`. `null` and `undefined`
stringify exactly as template interpolation did, so converting a call site
cannot change what the user sees.

## Why the catalog is checked in as one file

It is generated by merging per-unit entry files, then verified: the merge fails
if any `t("...")` in the source has no catalog entry, and reports keys that no
call site uses. Both directions matter — an unresolved key renders as a raw
identifier, and an unused key is dead weight that hides drift.

## When you add copy

1. Add the string with `t("area.file.name")` at the call site.
2. Add the entry to `packages/i18n/src/zh-CN.ts`, keeping it sorted by key.
3. `vp run --filter @t3tools/i18n typecheck` — the key type is derived from the
   catalog, so a typo or a forgotten entry fails here rather than at runtime.

## Finding copy is the hard part

The first pass through this fork scanned only `.tsx`/`.jsx`, on the assumption
that UI copy lives in components. It does not. Plain `.ts` modules hold a lot of
it, and the most damaging example was `apps/web/src/components/settings/settingsSearch.ts`:
a single `.ts` file that is the **sole source** of every settings title and
sidebar nav label. Missing it left the entire settings menu in English while the
descriptions beside it — which live in `.tsx` — were already translated. The
result read as a half-finished localization rather than a missed file.

Two further shapes are easy to miss, both found the same way:

- **Composed strings.** A label built by concatenating a translated fragment with
  an untranslated one renders as "Received 1 update and used 1 tool，工具调用失败".
  Grepping for the fragments' source modules is the only reliable way to catch it.
- **Shared packages.** `packages/client-runtime`, `packages/contracts` and
  friends produce copy that a component renders verbatim. They need their own
  pass; the app-level sweep will not find them.

When scanning for copy, cover `.ts` as well as `.tsx`, include `packages/`, and
verify by rendering the app rather than by trusting a count.

## Upstream merges

Every localized line is a divergence from upstream, so a merge will conflict
wherever upstream touched the same string. The catalog itself never conflicts
(upstream has no equivalent file), and the `packages/i18n` package is additive.
Expect the friction to sit in component files, in proportion to how much copy
they contain.
